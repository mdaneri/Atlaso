Appliance certificates with Atlaso¶

Use Atlaso as the issuing CA while the target appliance generates its own certificate signing request (CSR) and keeps its private key. Install the signed leaf certificate and public CA chain through the target's native administration workflow. Start with Certificate Authority for CA configuration and access.

Choose the certificate and trust operation¶

Operation Material and destination
Replace SRM appliance TLS SRM-generated CSR, signed leaf, and CA chain in the SRM certificate installer
Replace vCenter Machine SSL vCenter-generated CSR, signed leaf, and trusted root chain in Certificate Management
Trust the server from a browser or API client Verified public Atlaso root in that client's trusted CA store
Trust another server from an appliance Verified public CA certificates in the appliance's supported outbound trust store
Trust Atlaso from VCF Installer or SDDC Manager Use the separate VCF Certificate Trust workflow
Enroll a KMIP client Follow vSphere Key Providers, which has different certificate purposes

Include the public Atlaso root in the appliance's CA-chain input. If the root signs the leaf directly, the chain contains that root alone. With intermediate issuers, include the intermediates in issuer order, ending with the root. Keep the leaf separate when the installer has separate leaf and chain fields. Installing a chain does not establish trust in every browser, peer appliance, or outbound trust store; configure each relying party separately.

Download Download root CA from the Atlaso CA page and verify its SHA-256 fingerprint through an independently trusted record or appliance console before trusting it. Distribute only public certificates. The root private key stays in Atlaso; the target private key stays in the target appliance for the CSR workflows below.

The CA can issue and apply certificates with Listen interfaces empty. Select an eligible access interface only when you intend to publish its public certificate portal on that network. DNS listening is a separate service configuration; the dedicated management role is reserved for the management UI.

Prepare the target¶

  1. Record the exact product/version, certificate role, target VM identity, current certificate fingerprint, and recovery procedure. Schedule any required maintenance and preserve the vendor-supported backup or rollback point.
  2. Configure a proper appliance FQDN before requesting a certificate, for example srm.lab.example or vcenter.lab.example. Confirm forward DNS, any vendor-required reverse DNS, and resolution from the appliance and its clients. Do not use a factory localhost.localdomain identity for deployment.
  3. Record the exact names clients use. Include each required DNS name as a DNS SAN; include an address as an IP SAN only when clients connect by that address. An IP in Common Name or a DNS SAN does not replace an IP SAN.
  4. With DHCP, arrange an address reservation or managed DNS updates before relying on a persistent address. If the address changes, update DNS and replace any certificate whose IP SAN no longer matches.
  5. Verify current time on Atlaso and the target. Follow NTP and NTS; keep the intended clock source rather than enabling both NTPsec and VMware Tools clock synchronization.
  6. Verify the target's existing TLS identity before sending administrator credentials. For a factory certificate, establish its fingerprint through the verified appliance console or another independent trusted observation. Never substitute disabled TLS verification for identity confirmation.

Renaming a registered appliance may affect service registration and site pairing. Follow the version-matched vendor rename procedure first; issuing a certificate with a new name does not rename the operating system or update DNS.

Issue an appliance CSR through Atlaso¶

  1. Generate the CSR in the target appliance. Save the public PEM CSR and keep the corresponding private key there. Do not generate another CSR before installing the response: that can replace the key associated with the request.
  2. In Certificate Authority → Profiles, select a suitable enabled server profile or create a dedicated profile with + Add profile here. Match the vendor's algorithm, validity, key usage, extended key usage (EKU), and SAN requirements. Avoid changing a shared profile to satisfy one appliance.
  3. Open CSR Intake → Start CSR intake. Enter the common name, profile, description, DNS SANs and IP SANs, then paste the complete PEM CSR or select Upload a CSR file for a PEM-encoded .csr or .pem file up to 64 KiB. Review the populated CSR and identity, then select Stage CSR request. Confirm control of every SAN; the signed certificate's names must match the intended target, not merely the names an unverified CSR requests.
  4. Open Review appliance changes. Select Certificate Authority and inspect any required dependencies. Deselect unrelated pending units. Submit the reviewed plan and confirm its task succeeded before installing.
  5. In Certificate Requests, confirm the request is issued. Open its row menu and select Export → Certificate. Download the public root separately. Inspect any exported certificate chain before using it: an installer with separate inputs expects a leaf-only file and a CA-only chain file.
  6. Check the signed leaf against the original CSR: public key, subject, DNS/IP SANs, validity, issuer, key usages, EKUs, and non-CA basic constraints. Verify its signature chain against the expected public root.

If a newly added profile is missing from the CSR wizard, cancel the blank wizard and reload the CA page before starting intake again. Exporting a private key is unnecessary for an appliance-generated CSR.

Understand the downloaded files¶

Atlaso's Export → Certificate downloads a PEM-encoded leaf named <name>.pem. Older Atlaso releases downloaded the same PEM format with a .crt filename. PEM describes the encoding; a .crt extension alone does not mean the contents are binary DER. A PEM certificate contains -----BEGIN CERTIFICATE----- and -----END CERTIFICATE----- markers.

Download Filename Contents
Export → Certificate <name>.pem One PEM leaf certificate
Export → Certificate chain <name>-chain.pem PEM leaf followed by the Atlaso root for newly issued certificates
Download root CA atlaso-root-ca.pem Public PEM root certificate, without the leaf
Download CA bundle atlaso-ca-bundle.pem Public PEM root certificate in the current direct-root issuing model
Export → Private key <name>.key Separate PEM private key, available only when Atlaso generated and holds it

For a CSR generated in SRM or vCenter, Private key is disabled because Atlaso does not have that key. Use the target's signed-CSR response import option. These downloads are separate PEM artifacts, not a PKCS#12/PFX bundle.

For an older .crt download, if an import file picker requires .pem, save a copy of the already PEM-encoded file with a .pem extension. No encoding conversion is needed. Renaming a file does not convert DER or PKCS#12 into PEM, supply a missing private key, or change the certificate's usages.

For separate certificate and CA-chain inputs, use the leaf and Download root CA when Atlaso signs directly. Do not put Export → Certificate chain into a CA-only field: that export includes the leaf. Choosing a PKCS#12 import option instead of a signed-CSR option also requires a different artifact; renaming .crt to .p12 cannot produce one.

For these OpenSSL examples, save the public CSR as appliance.csr.pem and the downloaded leaf as appliance.pem. Keep the root's downloaded filename, atlaso-root-ca.pem. These commands inspect only public material:

openssl req -in appliance.csr.pem -noout -verify -text
openssl x509 -in appliance.pem -noout -text
openssl verify -CAfile atlaso-root-ca.pem appliance.pem

For an intermediate CA, supply its certificates with OpenSSL's -untrusted option when verifying the leaf. Compare the CSR and leaf public keys as well as reading their subjects; matching names alone do not prove a key match.

SRM and VCF Protection and Recovery¶

Select a profile and generate the CSR¶

Create a dedicated SRM Lab TLS server profile: RSA 2048, 365-day validity, SAN required, key usage digitalSignature,keyEncipherment,dataEncipherment, and EKUs serverAuth,clientAuth. Atlaso's default VCF service TLS profile has serverAuth only. Confirm the full requirements for your product/version and authentication mode against Broadcom's SRM/replication certificate guidance.

The initial installation-only lab test omitted dataEncipherment; it did not validate certificate-based site pairing. Include all three key usages when issuing a certificate for this workflow, and reissue an existing certificate that lacks a required usage before attempting pairing. Do not treat successful certificate import as pairing acceptance.

Generate the CSR through the appliance's supported certificate administration workflow. For automation, the configuration API CSR operation generates the key inside the appliance. For example, the API base for srm.lab.example is https://srm.lab.example/api/rest/configure/v2. On the tested Protection and Recovery 9.1.1 appliance, the configuration API served port 443; port 5480 served the management UI.

Use the authenticated configuration API session mechanism documented for your version. Keep passwords and session headers out of command arguments, URLs, saved request files, transcripts, and logs. The CSR input uses common_name, organization, organization_unit, country, fqdn for DNS names, and ip for IP SANs. Use the configured appliance identity and the verified address, for example srm.lab.example and 192.168.50.20.

Install and verify¶

  1. Issue the CSR through Atlaso as described above, including the SRM-specific profile, all three key usages (digitalSignature,keyEncipherment,dataEncipherment), and both required EKUs (serverAuth,clientAuth).
  2. Use the appliance's signed-CSR certificate import workflow. For the configuration API, send POST /api/rest/configure/v2/appliance/certificates/server with only the csr_format representation:
{
  "csr_format": {
    "certificate": "<signed leaf certificate PEM>",
    "ca_chain": ["<Atlaso root certificate PEM>"]
  }
}

Replace placeholders with PEM strings encoded by a JSON serializer. Include intermediate certificates if applicable. The native certificate update operation returns HTTP 204 on success. No private key upload is needed because SRM owns the CSR key. 3. Wait for the appliance endpoints to become ready. Make fresh TLS connections to ports 443 and 5480, verify the exact new leaf fingerprint, and validate the chain and requested hostname against the expected Atlaso root. 4. Sign in again and check native appliance health and version. Reconfigure registration and reconnect the site pair when required by the vendor procedure; then check replication and the supported recovery test separately.

Do not assume every release accepts the same PKCS#12/PFX format. Broadcom documents version-specific limitations in SRM/VLSR/replication CA certificate configuration. Prefer the native CSR response path when the appliance generated the request.

If SRM must connect to a vCenter that now presents an Atlaso-signed Machine SSL certificate, its outbound trust must also recognize that CA. This is distinct from installing SRM's own leaf and chain. Follow the version-matched SRM trusted-CA procedure and verify registration/site pairing afterward; do not infer trust-store contents from a successful leaf import.

vCenter Machine SSL¶

This section follows Broadcom's vSphere Client procedure for vCenter 7.x, 8.x and 9.x. It replaces Machine SSL; changing the VMCA root is a separate operation. Verify requirements for your exact build.

For Machine SSL, use serverAuth as the EKU; do not reuse the SRM profile's dual-purpose EKUs. Broadcom specifies an empty EKU or server authentication only for this role, while NSX cluster and some ESX client uses differ. See Broadcom's EKU requirements. Atlaso's VCF service TLS profile supplies serverAuth; check its other settings against your version's requirements.

  1. Prepare the supported backup and rollback point. For Enhanced Linked Mode, follow Broadcom's coordinated offline snapshot requirement for all linked vCenters. Disable vCenter HA as required by that procedure before rotation.
  2. Confirm the FQDN matches the Primary Network Identifier (PNID), resolves correctly, and appears in the DNS SANs. Wildcards are unsupported.
  3. As an authorized SSO certificate administrator, open Administration → Certificate Management → Machine SSL in the vSphere Client. Select the vCenter certificate and generate its CSR.
  4. Submit that CSR through Atlaso with a profile satisfying the vCenter certificate requirements. Verify the issued certificate and preserve the vCenter-owned key.
  5. Select Import and Replace Certificate, choosing the external CA option for a CSR generated by vCenter. This uses the private key retained inside vCenter. Supply only the leaf certificate and a separate trusted CA chain, including the Atlaso root. Complete the review and replacement.
  6. Reconnect with strict TLS, verify the served leaf and administrator login, and check dependent services.

For native API automation, generate the request with POST /api/vcenter/certificate-management/vcenter/tls-csr. Keep the returned CSR public and the generated private key inside vCenter. If Atlaso is not already trusted, import its verified public root using POST /api/vcenter/certificate-management/vcenter/trusted-root-chains with {"cert_chain":{"cert_chain":["<Atlaso root PEM>"]}}, then independently read back the stored root fingerprint. For a vCenter-generated CSR and an already trusted issuer, replace Machine SSL using PUT /api/vcenter/certificate-management/vcenter/tls with {"cert":"<signed leaf PEM>"}. The tested operation returned HTTP 204. Do not supply or export a private key for this path. Reconnect afterward with the expected CA and exact new leaf fingerprint, then establish a fresh administrator session and check appliance health.

In the tested IP-PNID lab, a certificate containing only the correct IP SAN was rejected with com.vmware.certificatemanagement.invalidargument.san.empty. Issuing the same vCenter-owned CSR with its existing PNID entered in both Atlaso's DNS SANs and IP SANs resolved that rejection. This is an observation for the tested build, not a reason to replace a deployment's FQDN with an IP address. Prefer an established FQDN/PNID and verify the actual issued SANs. Broadcom also documents SAN-empty import failures.

Replacing vCenter Machine SSL can require SRM or replication reconfiguration and site reconnection. Follow Broadcom's recovery procedure after a vCenter SSL change. Confirm outbound root trust on dependent appliances rather than accepting an unexpected fingerprint blindly.

Other appliances¶

Use the same CSR custody and Atlaso issuance steps when the product supports an external CA. Before installation, consult that product's version-matched instructions for certificate roles, SANs, EKUs, algorithm, chain order, import format, service restart, and dependent trust updates. ESX, NSX and other appliances have their own lifecycle rules; the SRM JSON body is specific to its configuration API.

For a product that requires an externally generated private key or PKCS#12, establish its supported secure key custody and import procedure first. A leaf certificate issued for one CSR cannot be paired with a different key.

Verify, renew, and recover¶

For a target whose leaf is signed directly by Atlaso, a fresh HTTPS check can use the verified public root:

curl --cacert atlaso-root-ca.pem https://srm.lab.example:5480/

Success requires both a trusted chain and a matching SAN. Verify the served leaf fingerprint independently of an HTTP success response, then check authenticated application health and each dependent integration. Trusting the root cannot fix a wrong hostname, missing EKU, expired certificate, or mismatched key.

Track expiry and renew early through the same appliance CSR workflow. After a hostname/address change, generate a new CSR and certificate for the new identity. Plan root rotation separately, distributing new trust before switching leaves and retaining required old trust during the transition.

If import fails, preserve the existing working configuration and inspect the CSR/key match, PEM format, chain, SANs, validity and profile. If services fail after replacement, use the recorded vendor recovery procedure and coordinated backup/rollback point. Restore registrations and peer trust as needed; do not replace unrelated certificates or disable validation to conceal the failure.

Validation coverage¶

The lab exercised Atlaso 0.9.446 with VCF Protection and Recovery 9.1.1.0100 build 25753785: native appliance CSR, RSA 2048, key usages digitalSignature,keyEncipherment, both TLS EKUs, leaf/root import, exact leaf fingerprint, strict CA and IP-SAN verification on ports 443 and 5480, and a fresh authenticated configuration API session. That initial test used the appliance's factory hostname; it establishes certificate installation, not readiness of that hostname for deployment.

The lab also exercised vCenter 9.1.1.0 build 25712839: native RSA 2048 CSR, Atlaso's VCF service TLS profile, verified root import/readback, Machine SSL replacement through the native API, exact new leaf and strict CA/IP-SAN verification on ports 443 and 5480, fresh administrator API login, and green appliance health. The final certificate included the existing IP PNID in both DNS and IP SANs; an earlier IP-only SAN attempt was rejected and left the original served certificate intact. The private key remained inside vCenter. The tested vCenter had no linked replication partners, no vCenter HA deployment, and no registered hosts or VMs, so this does not establish dependent workload or integration acceptance.

vCenter registration, site pairing, replication, recovery plans, other appliance products, and a renamed SRM require their own acceptance checks.
