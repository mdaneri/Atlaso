Offline installation ISO build and verification¶

This reference records the build and release path for issue #542. The development ISO from source commit 7df968dc3079f3e7cf09655e248d961b8bc05c9d completed two independent disconnected Auto installations through the default serial path in VMware, inspected with host source 9337eb391f4500ae3ae557b672074bba4abc79a8. Both booted without media, passed root/admin authentication and account challenges, matched all five installed-content measurements, and preserved their unselected disks. Public machine and SSH identities differed between installations; the first VM retained its identity across a later network boot. Three later certificate-pinned host OpenAPI samples passed, while an initial failed API probe and broader installer acceptance remain under investigation. Physical SATA/NVMe and wired-Ethernet acceptance remains outstanding. This VM result does not establish physical-platform support or complete issue acceptance.

For recurring admitted package refreshes, use the Offline installation ISO refresh workflow to review Photon drift, bind capture inputs, assemble development media, and follow the receipt-bound VMware validation phases.

For writing the completed image on Windows, macOS, or Linux, use Create an Atlaso installation USB.

USB image layout and readback¶

USB-capable assembly retains the existing ISO9660 level-3 payload and optical El Torito boot catalog. Its MBR maps partition 1 (type 0x17, start sector zero) over the complete ISO and partition 2 (type 0xef) over the existing EFI FAT boot image. The overlap is intentional: it exposes the same bytes to disk firmware and optical firmware. There is no GPT, separate USB image, extracted FAT32 payload, or supported legacy-BIOS bootstrap. Remastering derives the EFI partition's sector address from the final boot catalog, rather than copying offsets from the upstream ISO. Assembly reads back that address, length, image boundary and FAT header before accepting the output.

After authenticating and reconstructing an installation release, use the trusted checkout's locked Python environment:

python scripts/verify_installation_usb.py --image <verified-complete.iso>

The checker reports the exact image length/minimum device bytes and EFI partition sectors. It refuses an optical-only image, a mismatched disk/catalog offset, or a truncated EFI image. It does not authenticate a release signature, verify every installed payload file, or establish firmware compatibility; retain the existing release verifier first.

After writing, optionally add the operator-selected whole USB device to compare all ISO bytes read-only:

Host Device argument
Windows, elevated PowerShell --device '\\.\PhysicalDriveN' using the exact independently inspected USB disk number
macOS, Terminal with disk-read permission --device /dev/rdiskN after diskutil unmountDisk /dev/diskN for that inspected external disk
Linux, with disk-read permission --device /dev/disk/by-id/<exact-selected-whole-usb-identity>

These device names are selectors for an independently identified device, not stable identity proof. Never substitute a partition such as diskNs1 or a Linux -part1 link. The checker opens both inputs read-only, bounds comparison to the ISO length, rejects short/different reads, and reports the verified prefix's SHA-256. Extra USB capacity is outside that comparison. Reconnect/reselect deliberately if the operating system has changed enumeration. Writer validation and this byte comparison do not replace actual disconnected USB boot/install, source/unselected-disk preservation, USB-free reboot, payload, first-boot and host OpenAPI acceptance. Record physical USB 2/3 and SATA/NVMe hardware results separately.

Installer image contract¶

The installation image reuses the pinned Photon 5.0 ISO and Photon installer 2.2. Remastering preserves the source EFI boot image and native installer flow. The Atlaso deployment source comes from an immutable Git archive at the selected full commit. The signed software release, its exact application wheel, locked CPython wheelhouse, shared provisioning inputs, PowerCLI modules, trust material, notices, firmware, and a signed offline Photon RPM repository are embedded and inventoried. Dependency closure is resolved during authorized ISO preparation; installation does not use network package repositories. Shared provisioning explicitly installs iproute2 for the console and diagnostics; the final package-state verifier requires it. The complete captured RPM closure must include its dependencies. The boot package selection includes Photon’s native initramfs package and its resolved dependencies. Installation requires the kernel and initrd selected by Photon’s GRUB environment to exist before applying chosen credentials or reporting completion.

Installation requires at least one hardware-backed Ethernet adapter. The installer checks before disk selection and again immediately before partitioning. A disconnected cable, missing DHCP lease, or unavailable Internet does not block this offline installation. Add a VMware network adapter before booting a test VM; a loopback or software bridge alone does not satisfy the requirement.

During installation the active console displays Photon's native progress bar, counting completed installation stages. Stages have different durations; package and Atlaso software installation can take substantially longer than other steps. The bar reaches completion only after the native sequence, boot checks, account configuration, and unmounts succeed. In the VM window, use Alt+F2 for detailed installer/provisioner output and Alt+F1 to return to progress. Serial sessions keep their selected console; the progress screen identifies a private /run/atlaso-install-* log directory when a second virtual terminal is unavailable. Logs are volatile and contain no chosen account passwords.

The installed appliance enables real system adapters (ATLASO_DRY_RUN_SYSTEM_ADAPTERS=false), so global Appliance Apply executes the reviewed helper operations. Completion refuses a missing, simulated, or ambiguous persisted setting. This does not automatically apply pending configuration during installation. Existing appliances installed with an older ISO retain their original setting; producing a replacement ISO does not modify them.

Auto and Custom both offer named SFTP backup storage and VCFDT depot storage screens before destructive review. Keep the default to preserve an existing service partition or shared storage. Other choices explicitly assign a compatible Custom /mnt/ partition, or an otherwise unused disk as a full-disk ext4 partition at the fixed service mount. The installer does not infer roles from capacity, order, labels, or old filesystems. A previously selected disk cannot also be chosen for whole-disk replacement, and the two roles cannot take the same partition. Returning Back discards tentative choices; all selected identities and mount layouts still require the complete No-default review. These choices create the installation layout only; they do not enable the SFTP or depot service or expose credentials.

The shared boot-branding installer handles both native Photon kernel paths. The root-only Auto layout uses /boot/$photon_linux and points GRUB at /boot/grub2/themes/atlaso/theme.txt; a Custom layout with a separate /boot uses /$photon_linux and /grub2/themes/atlaso/theme.txt. Theme files remain under /boot/grub2/themes/atlaso in both layouts. Custom layouts must use ext4 for the boot filesystem; see Choose disks and layout. The installed boot entry is labeled Atlaso Appliance, including GRUB's text fallback; it must not be a blank entry.

Use the existing VMware build and lifecycle process for admitted Photon builders and VM validation. Do not create a parallel Hyper-V or KVM image pipeline. Capture RPM dependencies during preparation on the authorized Photon builder; do not restart or repurpose a consumed template to produce capture inputs. capture-rpms requires an absent absolute output directory. Task workspaces, temporary content, and validation output must stay under a configured permitted root. Receipt resource ownership and source/task identity before creating disposable roots, as required by the completed-task cleanup policy. Keep release signing inside the protected hosted workflow.

Prepare inputs¶

Use the full source commit and exact software version being prepared. Select an absent destination for each newly created output. Begin from authorized builder preparation state and capture the resolved, signed Photon RPM closure and required firmware:

python scripts/build_installation_iso.py capture-rpms --output <absent-absolute-directory>

Prepare the candidate from that closure, the exact signed software payload, and the PowerCLI modules accepted by the existing Validate mode of image/common/powershell/provision-powercli.ps1:

python scripts/build_installation_iso.py prepare --commit <FULL-SOURCE-SHA> --version <X.Y.Z> --payload <absent-directory> --software <verified-software-directory> --rpms <captured-rpm-directory> --powercli <validated-powercli-directory>

The preparation stage binds the source files to the selected commit and records the software, RPM, firmware, and PowerCLI inventories. Keep its unsigned candidate in the private task workspace; it is not a release artifact. For controlled transfer, package the candidate and split oversized input archives into an existing empty destination directory:

python scripts/build_installation_iso.py pack-inputs --payload <candidate-directory> --output <absent-archive.tar.gz>
python scripts/build_installation_iso.py split-inputs --archive <input-archive.tar.gz> --output <existing-empty-directory>

Input packaging does not grant signing authority. The protected installation-prerelease.yml workflow independently validates the candidate before loading signing material. Besides authenticating every RPM, validation tests the entire candidate as an RPM transaction against a fresh database containing only the admitted trust keys. All requirements, RPM capability requirements, and conflicts must pass with scripts, triggers, and plugins disabled. No host-installed package database or network repository can supply a missing dependency. An unsupported host RPM capability or incomplete closure stops validation. This check does not replace disconnected installation and reboot acceptance.

The workflow then signs the candidate, assembles the ISO, and stages the signed installation assets in the existing hidden installation-vX.Y.Z-rc.N draft. This staging run leaves the release as a draft. Installation artifacts remain separate from software-update and virtualization release assets. The signed release index covers the ISO manifest and assets; phase one requires Secure Boot disabled. ARM support is a possible second phase and is not included in the x86-64 release contract.

Development-only VMware test image¶

The existing PR builder accepts -CaptureInstallationRpms to download the resolved Photon RPM closure and installed PowerCLI modules. Pass an existing, empty, creation-receipted -InstallationCaptureDirectory and its original -InstallationCaptureRootIdentity. Keep this directory separate from the VM output: Packer removes temporary archive files from the VM output during cleanup. The capture directory preserves installation-rpms.tar and installation-powercli.tar for independent verification and ISO assembly. This option is rejected for release builders. Capture staging uses /var/tmp so it does not consume the guest's /tmp memory filesystem during shared provisioning. Use -Headless for unattended capture without opening the Workstation console. Independently validate all captured inputs before assembly; capturing files alone does not establish a successful appliance build.

Refresh the complete captured dependency closure when refreshing ISO contents, together with the eligible signed Atlaso software bundle and its locked CPython wheelhouse. Packages absent from current official Photon metadata require a fresh capture; do not suppress package admission or replace individual packages without verifying the complete set.

PowerCLI input can also be prepared with the existing locked module installer in a receipted task directory:

pwsh -NoProfile -File image/common/powershell/provision-powercli.ps1 `
  -Mode Install -ModuleRoot <TASK-OWNED-POWERCLI-DIRECTORY>

For installer work on a pull-request commit, use the explicit development builder. It requires a clean checkout at the exact PR HEAD; the separately supplied software directory must be a signed main release, with its version and main-reachable source commit passed independently. Reuse the already captured Photon RPM directory, validated PowerCLI modules, pinned Photon 5.0 source ISO, and verified software release. Put all paths under the configured, receipted task roots, and select absent payload and ISO destinations plus an existing empty private scratch directory:

python scripts/build_development_installation_iso.py `
  --commit <PR-HEAD-SHA> `
  --software-version <MAIN-RELEASE-VERSION> `
  --software-commit <MAIN-RELEASE-SHA> `
  --software <VERIFIED-MAIN-RELEASE-DIRECTORY> `
  --rpms <CAPTURED-PHOTON-RPM-DIRECTORY> `
  --powercli <VALIDATED-POWERCLI-DIRECTORY> `
  --payload <ABSENT-DEVELOPMENT-PAYLOAD-DIRECTORY> `
  --scratch <EXISTING-EMPTY-PRIVATE-DIRECTORY> `
  --source-iso <PINNED-PHOTON-5.0-ISO> `
  --output <ABSENT-DEVELOPMENT-ISO-PATH>

This builder uses the distinct atlaso-installation-development-public-test key identity. Its deterministic Ed25519 fixture seed is public test data (bytes(range(32)), bytes 00 through 1f); it is not a credential or release authority and is never stored as a secret. The production signer and default production verifier continue to require the production key identity. Production finalization runs only from main, uses its checked-out workflow tools, and retains the protected signing environment and main-release admission checks. The development initrd accepts the test identity only when its explicit development marker is present. The resulting image is for VMware testing only and starts the installer in the VMware window by default (console=tty0). Open the fresh VM with its ISO attached and power on; no GRUB edit is needed. The five-second GRUB menu offers VM window (tty0) and Serial (ttyS0, 115200) entries. Use the arrow keys and Enter to choose the installer console. Each entry selects exactly one kernel console. When serial initialization succeeds, the boot menu accepts input and displays output on both the VM window and COM1 at 115200 baud, 8N1; otherwise the native console remains available. Native logger propagation and Python prints are isolated from the progress terminal; detailed output remains available on the separate terminal or in the private volatile log. The VM-window installer keeps the kernel's detected terminal size; only the serial harness uses a fixed 80×25 size. Concealed account fields accept printable ASCII characters and preserve spaces exactly. Rejected password input is cleared before retrying. Go Back on confirmation returns to the first password field for that account; Go Back on the first admin field returns to the full disk review and requires a new Yes (the default remains No). Go Back on the first root field returns to admin password entry and discards collected passwords. No disk writes occur during these setup screens. Explicitly declining the disk review still cancels installation. Go Back from Custom partitioning returns to disk/layout selection and discards the abandoned partition plan. For the automated serial-console harness, add --serial-console to the development build command to make the serial entry the default; both entries remain available. The build result's console field records that default as graphical or serial, not a later operator selection. Retain the default, actual selected entry and exact ISO digest so validation for one console mode is not reported as validation of the other. Neither image is publishable as an Atlaso release or establishes production or physical-hardware acceptance.

Boot-time signature verification reuses the cryptography package already included in the pinned Photon initrd; that initrd removes the OpenSSL command-line executable. The downloadable verifier retains its existing OpenSSL path.

RPM repository generation explicitly uses gzip metadata so the pinned Photon initrd can read it, regardless of the build host’s default compression format. Repository configuration uses UTF-8 with LF line endings for Photon TDNF. The installed runtime uses the same current Photon 4096-bit RPM key as the shared repository initializer, with signature checking enabled. Legacy keys remain available to the pinned native installer where required.

The VMware harness initializes its RTC from host UTC (rtc.diffFromUTC = "0") because Photon reads the hardware clock as UTC. Verify that the host clock is correct before starting a disconnected installation. A clock behind the RPM signature creation time can cause native package verification to reject an otherwise authentic package; retain signature checks and correct the clock before retrying with a fresh installation fixture.

The VMware harness creates an isolated EFI VM with one disconnected E1000 Ethernet adapter, two blank SCSI disks, and a private serial console. Its VMX configuration uses UTF-8 to preserve non-ASCII worktree, ISO, and output paths. The serial reader recognizes the native menu's overwrite-mode reset and nonmoving character-set shifts when reconstructing visible disk rows. Unsupported modes still invalidate cursor certainty; a supported reset does not erase that uncertainty or authorize a guessed cursor-position reply. Hash the generated ISO and use the exact owning pull request number. Probe checks that the native Photon disk selection screen exposes both blank fixture disks, and Cancel checks cancellation before disk writes. Auto exercises the single-disk Auto installation path. Reboot, persistence, and Appliance Update checks remain separate follow-up tests:

Fresh VM creation requires 74 GiB free on its host volume: the 64 GiB target, 4 GiB unselected disk, 4 GiB memory backing, and 2 GiB overhead. Sparse disks grow during installation, so their initial file sizes do not establish sufficient host capacity. An installed-VM boot or inspection resume reserves 6 GiB for new memory backing and overhead; it does not reserve space for arbitrary future guest disk growth.

When the source volume lacks this capacity, a maintainer may explicitly approve a separate development VM root. Keep the configured Codex worktree root, source checkout, credentials, VNC client, and durable .task-ownership records in their original locations. Do not repurpose OwnershipRoot, move an existing VM, use a junction, or adopt an existing directory. The controlling task must create the approved empty root exclusively with the existing CreateAndPinOrdinaryDirectoryPath lifecycle helper and publish its original native identity in the creation callback, before using the directory. Preserve that receipt and its SHA-256 outside all VM removal roots.

The internal schema-1 root receipt uses phase installation-validation-root-created and kind artifact. It binds the task, repository, branch, source commit, worktree path and native identity, PR/local identity, approved root path and native identity, creation time, and supported artifact-root cleanup descriptor. Every operation validates the receipt, source ancestry, directory identities and output containment, retaining native pins through the operation. Only canonical installation-ISO VMs may use this development path. Ordinary VM output rules stay unchanged.

Pass -ValidationRootReceiptPath <ORIGINAL-ROOT-RECEIPT> and -ValidationRootReceiptSha256 <CREATION-TIME-SHA256> with the same output directory on every console, boot, resume, verification and cleanup operation. The bounded consumer forwards them to each lifecycle phase; VM records also bind the original root receipt. Missing, changed, mismatched or reconstructed provenance refuses the operation. Delete each VM with its existing receipt-bound cleanup operation before releasing the empty validation root.

$isoSha256 = (Get-FileHash -LiteralPath <DEVELOPMENT-ISO-PATH> -Algorithm SHA256).Hash.ToLowerInvariant()
.\scripts\windows\vmware\invoke-installation-iso-test.ps1 `
  -IsoPath <DEVELOPMENT-ISO-PATH> `
  -IsoSha256 $isoSha256 `
  -OutputDirectory <ABSENT-VM-OUTPUT-DIRECTORY> `
  -PullRequestNumber <OWNING-PR-NUMBER> `
  -Scenario Probe

Run -Scenario Cancel and -Scenario Auto in separate receipt-bound VM roots, following the VMware lifecycle procedure for each. Auto obtains administrator and root credentials through the existing supported Atlaso credential bridge and sends them only to concealed installer prompts; do not put passwords in command lines or logs. CancelReview selects the target and accepts the default No at the native Erase selected disks? confirmation. The same confirmation displays the selected disks and proposed layout; no typed acknowledgement is required. Large disk-identity summaries and custom layouts use native review pages before that final confirmation. Insufficient selects the fixture's four-GiB disk and requires the exact capacity refusal for that disk before consent. Both scenarios use no credentials and compare both disks with their pre-boot baselines after stopping the VM. The native capacity dialog identifies the selected disk and its size. The console test reads all four complete message rows inside the native panel border and still requires the exact selected disk and byte count. Enter returns to explicit disk selection; Escape cancels before credentials or disk writes. CustomCancel opens the native partition editor, requires its complete empty-layout refusal, then uses Go Back. It obtains no credentials and compares both stopped disks. CustomAliasProbe submits /srv in the native Create New form and requires the complete Use /var/srv; /srv is a symlink. refusal, including its native wrapped display and the form controls. It then stops the VM and compares both disks; it sends no credentials or erasure consent. The public observer requires the whole message across adjacent display rows within that form. Its numeric cursor parser remains unchanged and does not assign widths to unknown characters. CustomReboot creates one remaining-size ext4 root partition on the fixture's selected 64-GiB disk through the native Create New form. Before consent it requires the complete review: that exact disk, only the native 10-MiB EFI partition and remaining-size root, the full erasure warning, and the default-No instruction. Additional disks or partitions, paged or incomplete reviews, and different filesystems fail this deliberately narrow scenario. The four-GiB disk remains independently unselected. Each public Custom phase has a 90-second limit clipped to the original overall deadline. Fixed phase checkpoints identify an incomplete native state without printing console contents or extending the test. Use a fresh receipt-bound VM directory for each scenario, with the same ISO identity and validation-root selectors as Probe. For a full Custom install, replace -Scenario Probe with -Scenario CustomReboot and append -InspectInstalled -InspectContent -InspectionPythonPath <ABSOLUTE-PREPARED-PYTHON-EXECUTABLE>. It uses the existing concealed credential bridge, media-free reboot, root/admin challenges and content checks below. These scenarios provide automation for their stated fixtures; adding them does not establish native or physical acceptance, multi-disk Custom coverage, Update persistence, or rollback coverage. MultiProbe and CustomMultiReboot select an explicit three-disk fixture: the original 64-GiB boot/root disk, the original 4-GiB unselected disk, and an 8-GiB selected data disk. Creation requires 82 GiB of host free space; the original two-disk gate remains 74 GiB. The fixed profile is recorded in both original VM and baseline receipts before use. Existing operations derive it from those sealed receipts; missing legacy profile fields admit only the original two-disk recipe. Profiles are never inferred from a current VMX or transferred between VMs. MultiProbe obtains no credentials and verifies all three stopped disks against their original baselines. CustomMultiReboot creates a remaining-size ext4 root on the 64-GiB disk and a remaining-size ext4 /var/srv on the 8-GiB disk. Its complete review must identify exactly those two disks and the native EFI/root/data partitions before Yes. The 4-GiB disk remains independently unselected and is compared after installation and media-free reboot. Use a fresh receipt-bound directory and -Scenario CustomMultiReboot with the same inspection options as above. The Custom editor rejects symlink mount targets from the authenticated Photon filesystem RPM before consent. For example, /srv is a native alias for /var/srv; enter /var/srv explicitly so the reviewed path matches the installed filesystem. Reserved live-system paths and noncanonical paths are also refused. Cancellation checks include every selected disk as well as the unselected disk. A mismatched profile, missing disk, extra disk or partition, changed path or size, truncated review, or additional device fails admission. Creation records a separate disk-baseline receipt before first boot. Retain both original receipt paths and their creation-time hashes from the console driver's ownership output. The console runner automatically verifies disks within its process deadline. To repeat verification afterward:

.\scripts\windows\vmware\test-installation-iso.ps1 -Mode Verify `
  -OutputDirectory <EXACT-VM-OUTPUT-DIRECTORY> -PullRequestNumber <OWNING-PR-NUMBER> `
  -OriginalReceiptPath <ORIGINAL-RECEIPT> -OriginalReceiptSha256 <ORIGINAL-RECEIPT-SHA256> `
  -BaselineReceiptPath <BASELINE-RECEIPT> -BaselineReceiptSha256 <BASELINE-RECEIPT-SHA256>

Background VNC console checks¶

The built-in Workstation VNC server can be controlled with a command-line client without using the host keyboard or mouse. Keep the original VM and disk-baseline receipts. Configure only that stopped VM, use an unused port bound exclusively to 127.0.0.1, and verify the live listener belongs to its exact VMX. Keep the fixture's sole E1000 adapter disconnected (ethernet0.startConnected = "FALSE"); console admission refuses a connected adapter or extra adapters. Use the default graphical development ISO for this path; it selects console=tty0 without an override. On images built with --serial-console, select VM window (tty0) from the boot menu and record that non-default selection. Historical serial images without this menu require a one-boot GRUB edit to use console=tty0 for a graphical test; record that override rather than claiming default graphical startup.

For an initial installer password field, VncCredential reuses the bounded SDK bridge, source/runtime pins, native provider verifier and concealed-field byte encoder. Its optional client is VNCDoTool 1.4.2, installed with its dependencies into an isolated, creation-receipted task virtual environment under the seven-day package-age policy. Record the original client package inventory with Get-AtlasoSourceSnapshotInventory from Atlaso.SourceSnapshot.psm1. Ordinary application installs do not require this client. The frame tests require its optional Pillow dependency and are run in the prepared validation environment. Set TMP and TEMP to an existing, creation-receipted task temporary root before invoking the consumer. The SDK bridge finishes its durable marker publication and cleanup before VNC source/runtime pins are held; the pins and frame checks still precede credential transmission.

First observe and capture the empty, concealed password prompt through the receipt-bound VNC connection. Review its account label and input focus, retain the image's SHA-256, and identify only its single input-row rectangle. Never admit a shell, ordinary text field, or arbitrary unreviewed screenshot. The adapter compares the complete live screen outside that small rectangle before requesting stdin and again before typing. It clears any previous retry text, checks the frame again, and submits only the selected SDK value. Passwords never enter arguments, environment variables, screenshots, ordinary files or diagnostic output. An unexpected frame, peer, source or runtime refuses submission; do not replace the recorded digest merely to make a refusal pass. Each screen check uses a fresh read-only VNC connection because the pinned client waits on empty updates from an unchanged VMware screen. All key events stay on the original admitted connection, with the client's native Shift option enabled for uppercase and shifted ASCII symbols.

.\scripts\windows\vmware\invoke-installation-iso-test.ps1 `
  -Scenario VncCredential -TimeoutSeconds 600 `
  -IsoPath <ORIGINAL-ISO-PATH> -IsoSha256 <ORIGINAL-ISO-SHA256> `
  -OutputDirectory <EXACT-VM-OUTPUT-DIRECTORY> -PullRequestNumber <OWNING-PR-NUMBER> `
  -CollisionSuffix <ORIGINAL-SUFFIX> `
  -OriginalReceiptPath <ORIGINAL-RECEIPT> -OriginalReceiptSha256 <ORIGINAL-RECEIPT-SHA256> `
  -BaselineReceiptPath <BASELINE-RECEIPT> -BaselineReceiptSha256 <BASELINE-RECEIPT-SHA256> `
  -VncAccount admin -VncPort <LOOPBACK-PORT> `
  -VncScreenPath <REVIEWED-EMPTY-FIELD-PNG> -VncScreenSha256 <RECORDED-PNG-SHA256> `
  -VncFieldRectangle <X0,Y0,X1,Y1> -VncPythonPath <ISOLATED-VENV-PYTHON> `
  -VncRuntimeSha256 <ORIGINAL-SITE-INVENTORY-SHA256> -VncRuntimeFileCount <ORIGINAL-FILE-COUNT>

AdmitConsole in test-installation-iso.ps1 provides the existing running VM's read-only admission for this operation. It requires the initial connected ISO, original receipts, persistent identity, exact disk bindings, isolated EFI configuration and exact running provider. It neither stops the VM nor verifies logical disk contents. Continue to use Verify after stopping or cancelling, and preserve the separate disk-comparison result.

After the VNC-driven installation completes, stop that exact VM with the owning verifier and release the initial private serial-pipe controller. Use BootInstalled on the same original VM and baseline selectors to create the existing media-disconnection receipt, reboot without the ISO, and run the ordinary root/admin challenges. Add -InspectInstalled -InspectionPythonPath <PREPARED-INSPECTION-PYTHON> for the existing identity and application payload checks. Preserve the emitted boot receipt and its creation-time digest for later LoginInstalled resumes. This scenario creates no replacement VM and does not repeat disk partitioning or password collection.

Installed-system checks¶

Use -Scenario AutoReboot in a fresh VM root to install, stop, disconnect the installation CD drive, and boot the installed system. This development image enables the standard password-protected serial-getty@ttyS0 service only after verifying the development signing identity, non-production marker, and VMware platform. It also invokes the shared boot-branding helper's explicit development option to add GRUB serial output and the ttyS0 kernel console. Production images keep their existing boot console and do not enable this test login service. The runner rechecks its private pipe peer before sending either chosen password to ordinary Linux login; it records only fixed success checkpoints, never the console stream. Login troubleshooting reports only fixed PAM and shell-stage categories. These diagnostics neither expose console contents nor establish successful authentication; the account-identity challenge must still pass.
